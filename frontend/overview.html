What this is

Does reweighting several public forecast models against one site's own observation history beat simply picking the single best model there?

That is the whole hypothesis. The maths is old — this is ensemble weighting, close kin to MOS. The part worth testing is whether it still helps when the weights are fitted per site, per lead time, against the customer's own sensor, and whether the size of the help is worth selling.

This is a backtest, not a forecast.

Nothing on either page predicts anything. Every number is what these models already said, scored against what the station already measured. It is a feasibility demo at one site over — days — not a result.

Section 2

What a blend is, in plain words

A blend is a weighted average of several models' forecasts for the same moment. A weight is that model's share of the answer. The weights sum to 1, so a blend is a recipe, not an addition: giving one model more means giving the others less.

The search grid step is 0.1, so weights move in tenths. Over — models that is — weight vectors, and every one of them is evaluated. There is no optimiser and no local minimum to worry about — the space is small enough to enumerate exhaustively. The pure single models are the one-hot corners of that same grid, so they are scored by exactly the same code path and appear in the same ranking.

Section 3

How it was measured: the join, and the split

The ±30 minute join, and why it has to exist

METAR observations are not reported on the hour. The station reports at roughly :52. A model valid time of 18:00Z therefore has no observation at 18:00Z — an exact-timestamp join between forecasts and observations matches zero rows. And a zero-row join does not error; it scores perfectly, because the mean of an empty set of errors is vacuously excellent. A silent, confident, entirely fake result is the failure mode here.

The join is therefore: for each model valid time, take the nearest valid observation within ±30 minutes, record the signed offset in minutes on every matched row, and raise hard if the matched count falls short. Observations are never interpolated — a missing observation is dropped, never invented, because an invented observation is indistinguishable from a real one downstream.

Fit on the first days, score on the last

Weights are fitted on the first — days and evaluated on the remaining —. Fitting and reporting on the same — days would guarantee an improvement by arithmetic alone: with every vector searched and only one metric, the best in-sample blend is at worst equal to the best in-sample single model, always, on any data whatsoever. That number would carry no information. "Fit on the first days, still ahead on the last" is the only version of this claim that survives a hostile question.

The split is —, not a random shuffle, because a random split would leak tomorrow's weather regime into today's training set.

Section 4

How to read a result

In-sample means measured on the days the weights were fitted on. Out-of-sample means measured on days the fitting never saw. The headline number is always out-of-sample; the in-sample number sits beside it, labelled. The gap between them is a displayed result rather than a hidden detail — it is the honest measure of how much of the fit was the site and how much was the fitting.

The winner rule is deliberately unfair to the blend

Two different selections happen, on purpose, in two different directions. The winner is the blend with the lowest in-sample error — chosen on the training days, without seeing the test days — and it is then reported out-of-sample. The baseline is the single model with the lowest out-of-sample error — chosen with hindsight, on the very data it is scored on. So the baseline gets to cheat and the blend does not. That is the conservative direction, and it is the only reason a positive improvement figure means anything at all: it says the blend beat a baseline that was handed the answer key.

Why the winner is not row #1

The leaderboard on the live page is sorted by out-of-sample error, but the winner was picked in-sample. Those are different orderings and they routinely disagree. At the selected lead time the winner (—) ranked — of — out-of-sample — so there were blends that scored better on the unseen days than the one the training window selected. Never describe the winner as "the best blend". It is the blend a forecaster restricted to the training window would have chosen, which is the only kind of blend anyone could actually have used in advance.

The chart is a two-model slice, not the whole search

With four models the weight space has three free dimensions and no single x-axis to plot error against. The chart therefore holds two of the four models at zero and sweeps the weight of one model from 0% to 100%, with the other taking the remainder. Both ends of the curve are genuinely pure single models.

Section 6

Most of the gain is from dropping GFS, not from the fitted weights

This is the section to read before quoting any number above. The obvious hostile question is "did you just discover that GFS is bad at this site?" Largely, yes. That was tested directly rather than left to argument.

Take an un-fitted blend — no optimisation, no training window, no search — that simply drops GFS and averages the other three models roughly equally: the nearest point on the grid to equal thirds. It is a real point on the same lattice, so it is scored by the same code as everything else. Then compare it, out-of-sample, against the fitted winner and against the best single model.

The verdict, assembled from the data at load time

Read that honestly and it says three things. One: the un-fitted blend captures most of the improvement at every lead. Two: therefore the headline improvements in section 5 should not be attributed to the precise fitted tenths. The weight search is not what produced most of the gain — excluding a badly-behaved model and averaging the rest produced most of the gain, and that requires no fitting, no training window, and no per-site service. Three: the narrower claim that survives is does per-site reweighting add value on top of a naive drop-the-worst-model average? — and on this run the answer is —.

None of this makes the headline numbers wrong. They are what the specified procedure produced. But a reader who takes "site-tuned blending gains double digits" away from this page has taken away more than the experiment showed.

Why GFS is bad here, and why it is not a bug

GFS's error at this site is a diurnal amplitude error: it runs warm in the local afternoon and evening and cold overnight, over-amplifying the daily temperature swing. This was checked against the alternative explanation — a decode fault — and rejected: GFS decodes correctly at the acceptance anchor to a physically sane value, and its range over the window sits alongside the observed range. The values are real. They are a coarse grid cell roughly 13 km from the station behaving like a coarse grid cell 13 km from the station.

GFS was included in the study and simply earned zero weight. It was not excluded, not dropped for coverage, and not filtered out. It was scored at every lead and its numbers are on the live page. Receiving weight 0.0 from the search is a result, not an exclusion. The results document records —.

What this is not

  • The split is not optional. Weights are fitted on the first — days and scored on the last —. Fitting and reporting on the same days would guarantee an improvement by arithmetic alone.
  • These samples are not independent. Four initialisations a day gives — forecast-observation pairs at this lead, but samples within a single day share a weather regime. The effective sample size is closer to — independent-ish days. Every confidence claim on this page should be read against that number, not against the pair count.
  • Nearest grid cell, no interpolation, and an unmeasured elevation gap. Each model's forecast is taken from its nearest grid cell to the station, with no horizontal interpolation and no elevation or lapse-rate correction. Because the four models sit on four different grids, each nearest cell is at a different model terrain height. The grid-cell terrain height was never fetched, so no terrain delta was measured and none is stated. A named unmeasured gap is worth more than a plausible invented number.
  • Reproducibility is bounded by the wall clock. The window is derived from the current time at fetch, so a later re-run scores a different month and produces different numbers. This page is bound to the served document rather than to any figure typed into it, which is why it cannot go stale silently.

Section 7

Where this goes

Per-site, per-lead weights are the product. Not the chart, not the leaderboard — the vector. A customer with a sensor and a forecast feed wants one answer: for this site, at this lead time, how much of each model should I be listening to? That answer is a few numbers, it is different at every site, and it goes stale — which is what makes it a service rather than a report.

The integration surface already exists. The page you are about to open is a static file reading a single endpoint, and that endpoint is the whole contract:

GET /api/results

{
  "meta":       { site, variable, units, window, init_runs,
                  source, generated_at, is_synthetic,
                  models_included, models_excluded, split },
  "lead_times": [ ... ],
  "results": {
    "<lead>": {
      "n_samples":         { train, test },
      "join_diagnostics":  { matched_pct, mean_abs_offset_min },
      "models":            [ { model, mae, rmse, bias, coverage_pct } ],
      "blends":            [ { rank, weights, label, is_pure,
                               mae_in_sample, mae_out_of_sample,
                               rmse_out_of_sample, bias_out_of_sample } ],
      "best_single_model": { model, mae_out_of_sample },
      "winner":            { label, mae_out_of_sample,
                             improvement_pct_vs_best_single }
    }
  }
}

That shape is locked and re-validated on every request; the backend returns an error rather than serving a document it cannot vouch for. For a partner integration, the interesting object is winner.weights per site per lead — everything else on this page is the evidence that the vector is worth having.

What is honestly required before selling it, on this evidence: more sites, a longer window, and the increment measured against the naive drop-the-worst-model baseline in section 6 rather than against a single model. That is the number a buyer should be shown, and it is smaller than the one in section 5.
