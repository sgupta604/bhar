Section 2

What a blend is, in plain words

A blend is a recipe: each model gets a share of the answer, and the shares add up to one.

Give one model more and the others get less. Shares move in tenths, so with — models there are — recipes, and we score every one. A model alone is just the recipe where it takes everything.

Section 3

How we graded them

We wrote the recipe using the first — days, then tested it on the last — — days the recipe had never seen.

Matching a forecast to a reading

The airport reports at about 52 minutes past the hour, so a forecast for 18:00 has no reading at 18:00. An exact clock match matches nothing — and nothing scores perfectly, because the average of no errors is zero. So we take the nearest reading within 30 minutes, and stop the run if too few match. Missing readings are dropped, never invented.

Fit on the first days, score on the last

Doing both on the same — days would guarantee a win by arithmetic alone. The split is by date — —, not shuffled — so the recipe never trains on the weather spell it is tested on.

Section 4

How to read a result

Every headline number is measured on days the recipe had never seen — and the model we compare it against was handed the answer key.

The winner rule is deliberately unfair to the blend

Our blend is chosen on the training days and reported on the unseen days. The single model it is compared against is chosen with hindsight — the best one on the very days it is scored on. The baseline cheats; ours does not.

Why the winner is not row #1

The leaderboard is sorted by unseen-day score; the winner was chosen on training days. Here it (—) came — of — on the unseen days. Never call it "the best blend."

The chart is a two-model slice, not the whole search

Four models means three dials and no single axis. The chart holds two at zero and slides the share between the other two. Both ends are pure single models.

Section 6

Most of the gain is from dropping GFS, not from the fitted weights

Read this before quoting any number above: most of the gain comes from not using GFS at this airport, not from our weights.

The hostile question is "did you just discover that GFS is bad here?" Largely, yes. So we tested it. Take a blend with no fitting at all that just drops GFS and averages the other three, scored by the same code as everything else.

The verdict, assembled from the data at load time

So section 5's numbers are not the reward for getting the tenths right. Dropping a bad model and averaging the rest did most of the work — and that needs no per-site service to sell. The claim that survives: does per-site reweighting add anything on top of just dropping the worst model? On this run, —.

The numbers are not wrong. But anyone leaving this page saying "site-tuned blending gains double digits" has taken away more than the experiment showed.

Why GFS is bad here, and why it is not a bug

GFS runs warm here in the afternoon and cold overnight: it exaggerates the daily swing. Not a decoding fault — its values are sane and its range matches the observations. It is a coarse grid cell 13 km away, behaving like one.

GFS was in the study throughout and earned a weight of zero. Not excluded, not dropped for missing data, not filtered out — earning zero is a result. The document records —.

What this is not

  • The split is not optional. Written on the first — days, scored on the last —. Both on the same days is a guaranteed win.
  • These samples are not independent. Four runs a day gives — pairs, but same-day pairs share the same weather. The honest sample size is nearer — days. Judge confidence against that.
  • Nearest grid cell, and an unmeasured height gap. No correction for distance or elevation, and four models means four grids. We never fetched those terrain heights, so no gap is stated. A named unknown beats an invented number.
  • A re-run will not reproduce these numbers. The window follows the clock, so a later run scores a different month.

Section 7

Where this goes

The product is the recipe itself — a handful of weights per site, per lead time — and we can produce one for any location with a sensor.

Not the chart, not the leaderboard. A customer with a sensor wants one answer: at this site, this far ahead, how much should I listen to each model? A few numbers, different everywhere, and they go stale — which makes it a service, not a report.

The integration already exists: one endpoint, and that endpoint is the contract.

GET /api/results

{
  "meta":       { site, variable, units, window, init_runs,
                  source, generated_at, is_synthetic,
                  models_included, models_excluded, split },
  "lead_times": [ ... ],
  "results": {
    "<lead>": {
      "n_samples":         { train, test },
      "join_diagnostics":  { matched_pct, mean_abs_offset_min },
      "models":            [ { model, mae, rmse, bias, coverage_pct } ],
      "blends":            [ { rank, weights, label, is_pure,
                               mae_in_sample, mae_out_of_sample,
                               rmse_out_of_sample, bias_out_of_sample } ],
      "best_single_model": { model, mae_out_of_sample },
      "winner":            { label, mae_out_of_sample,
                             improvement_pct_vs_best_single }
    }
  }
}

The shape is re-checked on every request. The object that matters is winner.weights.

Before selling it we need more sites, a longer window, and the gain measured against section 6's drop-the-worst-model baseline — a smaller number than section 5's.
