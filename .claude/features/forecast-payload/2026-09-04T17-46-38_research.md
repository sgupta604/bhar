## The look-ahead-bias trap — verified, with the real numbers

`results["<lead>"].blends[]` is sorted by **out-of-sample** MAE ascending
(`backend/contract.py:_validate_blends` enforces the sort). The **fitted** winner is the blend that
minimises **in-sample** MAE, and `backend/contract.py:_validate_lead` enforces exactly that:

```
best_in_sample = min(float(b["mae_in_sample"]) for b in blends)
if float(winner_blend["mae_in_sample"]) > best_in_sample + FLOAT_TOL:  -> ContractError
```

It also guarantees the label is unique (`matches = [b for b in blends if b["label"] == winner_label]`;
`len(matches) != 1` fails with *"...so the UI can find its row without using index 0 (D13)"*).

**Measured from `data/results.json` in this worktree** (`lead_times = [6, 12, 24]`,
`models_included = ["HRRR","GFS","NAM","NBM"]`, 286 blends per lead):

| lead | `winner.label` | fitted weights (H/G/N/NBM) | in-sample | out-of-sample | leaderboard rank | **`blends[0]` is instead** |
|---|---|---|---|---|---|---|
| 6 h | `HRRR 50 / NAM 10 / NBM 40` | .5 / 0 / .1 / .4 | 1.7793 | **1.9173** | 5 | `HRRR 70 / NBM 30` (.7/0/0/.3) |
| 12 h | `HRRR 60 / NAM 10 / NBM 30` | .6 / 0 / .1 / .3 | 1.9730 | **1.9661** | 23 | `HRRR 30 / NAM 40 / NBM 30` |
| 24 h | `HRRR 50 / NAM 10 / NBM 40` | .5 / 0 / .1 / .4 | 2.0141 | **2.1066** | 5 | `HRRR 40 / NAM 30 / NBM 30` |

`best_single_model` is **HRRR at every lead** (2.1075 / 2.2814 / 2.5231);
`improvement_pct_vs_best_single` = **+9.0249 / +13.8205 / +16.5075**; `n_samples = {train: 80,
test: 40}` at every lead. **Using `blends[0]` would silently ship a different blend at all three
leads and would be invisible in the output.** The label match is the only correct lookup.

*Label format note (for the fixture):* labels are model name + integer percent for every **nonzero**
weight, canonical order, `" / "`-joined; a pure corner is `"HRRR only"`
(`backend/make_fixture.py:38-46`). Zero-weight models are omitted — GFS never appears.

## Exact `backend.contract` symbols F3 imports

```python
from backend.contract import ContractError, load_and_validate   # weights.py — the ONLY import needed
```

`forecast/contract.py` **mirrors, does not import**, the private helpers (`backend/contract.py`
declares `__all__ = ["ContractError", "validate_results", "load_and_validate"]`; `_fail`, `_mapping`,
`_exact_keys`, `_sequence`, `_number`, `_integer`, `_text`, `_boolean`, `_utc_stamp` are private and
`backend/` is off-limits to edit — importing privates across a package boundary would make F3 a
reason someone edits `backend/contract.py` later). Re-exporting `ContractError` itself is the one
sensible reuse: one exception type means F4 has one `except` clause for both payloads.

**Validator skeleton to mirror** (`backend/contract.py:80-140`):

```
class ContractError(ValueError)                 # message ALWAYS begins with the JSON path
def _fail(path, message) -> None: raise ContractError(f"{path}: {message}")
def _exact_keys(value, path, expected) -> dict  # missing -> "missing required key(s) [...]"
                                                # extra   -> "unexpected key(s) [...]; the shape is locked"
def _mapping/_sequence/_number/_integer/_text/_boolean/_utc_stamp(...)
FLOAT_TOL = 1e-9        # weight-sum identity
BLEND_TOL = 1e-6        # §9 rule 6, blend_f identity — NEW, and deliberately looser
def validate_forecast(doc: dict) -> None
def load_and_validate_forecast(path) -> dict    # OSError -> "cannot be read"; JSONDecodeError -> "is not valid JSON"
```

`_exact_keys` is the mechanism that makes §6.2 executable: `p90` at any level is an *unexpected key*
and fails with its path. **Every level must go through `_exact_keys`** — a level validated with only
"required key" checks would let `confidence_pct` through.

## Patterns to Follow

- **`backend/contract.py` wholesale** — `_fail(path, msg)`; exact key sets per level; a module
  docstring stating *why* the file exists; explicit notes on what is deliberately **not** checked
  (there: the sign of `improvement_pct`; here: the same — a zero or negative `improvement_pct` is a
  legal result and the validator must never demand a win).
- **`forecast/cycle.py`** — pure by construction, every instant an argument, guards that raise
  `ValueError`/`RuntimeError` with a message citing the clause (`"FORECAST-SPEC §5.2: ..."`).
- **`score/run.py:write_atomic`** — validate first, then `tmp.write_text(...)`, then
  `os.replace(tmp, path)`. Nothing is written on failure. Add a `_require()`-style message when
  `data/results.json` is missing: say what produces it, do not traceback.
- **`backend/make_fixture.py`** — the fixture is loud: `is_synthetic: true`, `source:
  "synthetic_fixture"`, site name suffixed `(SYNTHETIC FIXTURE)`, and headline numbers that cannot be
  mistaken for real MAEs.
- **`tests/test_results_contract.py`** — a `valid_doc` module fixture, a per-test `deepcopy`, and a
  `_message(doc)` helper that asserts on the **message text**, not merely that something raised.
  *"A validator that rejects everything for the wrong reason is worse than no validator."*
- **F2's injected-fetcher stub that raises a non-`RuntimeError` exception** — the unambiguous
  zero-network proof, for `refresh.py`'s tests.
- **`fetch.grib._as_utc` / `valid_time`** — one implementation of the naive-is-UTC rule, imported,
  never reimplemented (`forecast/cycle.py:31` sets the precedent).

## Patterns to Avoid

- **`blends[0]`, or any rank/leaderboard heuristic, to find the fitted vector.** Verified wrong at
  all three leads. Also on the retrospective list already (`RETROSPECTIVES.md`, `demo-shell`).
- **Bare `assert`** anywhere in `forecast/` — stripped by `python -O`; T29 fails the build.
- **The substring `renorm` in executable code or in a raised message string** — T29 fails on it.
  (Docstrings and comments are stripped by the scanner, so prose is safe, but do not rely on it.)
- **`datetime.utcnow()`**, Kelvin constants, hardcoded GRIB message numbers — all T29 failures.
- **Reading `48` / `3` / `16` out of the spec as constants** — F2's `step_grid()` /
  `derive_horizon()` are the source of truth; the probe table is data, not prose.
- **Reading F2's plan §2.3 "contiguous from `grid[0]`"** — stale and self-contradictory; it would
  collapse `gaps` to permanently empty. Use trailing truncation.
- **Rescaling weights over the members that happened to arrive** — a different blend, whose skill
  numbers do not apply (D11).
- **`tests/test_build.py`** — already taken by `score/build.py`.
- **Comparing `GRIB_shortName` to `"t2m"`** — `"2t"` on valid data; F3 touches no GRIB anyway.

## Recommended Approach

Build **contract-first**, exactly as T3 and F2 did: write `forecast/contract.py` and its negative
tests before `build.py` exists, then `weights.py` (pure, verified against the real `results.json`),
then `make_fixture.py` (which gives F5 a green payload without F2), then `build.py` against the real
64-record cache already on disk, then `refresh.py` as the thin CLI that wires `select_cycle → build →
validate → write_atomic`. `contract.py` mirrors `backend/contract.py`'s structure symbol for symbol
but **imports only `ContractError` and `load_and_validate`** across the boundary — F3 must never
become a reason to edit an off-limits file. The single highest-value test is the `blend_f` identity
run over the real cache: it is the one check that makes the displayed number provably the weighted
sum of its members.

## Scope: **L**

Five new modules and five new test files, ~34 named tests before the plan adds its own, one locked
JSON contract with eleven rules, and two conventions that must be bridged carefully (model-key
casing, rounding). Smaller than F2 — no network, no threading, no cache, no probe, and every input
already sitting on disk — but larger than a typical ticket because the validator is broad by design
and the acceptance floor is unusually specific. Expect the test count to run well past the list
above, as F2's did.
