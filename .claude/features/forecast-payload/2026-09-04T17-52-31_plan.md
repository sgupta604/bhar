## Architecture

### Summary

F3 turns already-fitted weights into a forward document and makes FORECAST-SPEC §9 executable.
`weights.py` reads `data/results.json` through `backend.contract.load_and_validate` and extracts the
fitted vector per lead **by matching `winner.label` against `blends[].label`** — never by index.
`contract.py` is the pure, stdlib-only validator: exact key sets at every level (which is what makes
§6.2's ban executable), the `blend_f == Σ w·m` identity at 1e-6, and the rule-8 disjoint/total sweep
over the grid derived from `meta.step_h`/`meta.horizon_h`. `build.py` joins an F2 `CycleResult` to
those weights, bridges lowercase↔UPPERCASE model keys, and validates before returning.
`make_fixture.py` fabricates a loudly-synthetic document that passes the same validator with no
network, no cache and no `results.json`. `refresh.py` is the one CLI: `select_cycle → build →
validate → atomic write`.

### Module dependency direction (acyclic, deliberate)

```
forecast/contract.py   -- pure, stdlib only, NO I/O except load_and_validate_forecast.
      ^        ^          Owns the §7 banding primitives so builder and validator cannot drift.
      |        |
weights.py   build.py --> forecast/live.py, forecast/cycle.py (F2, consumed UNCHANGED)
      ^        ^      --> fetch.grib (_as_utc / valid_time only; fetch/ is READ-ONLY)
      |        |
      +-- refresh.py, make_fixture.py
```

**Decision D-F3-A — the §7 banding table has exactly one implementation.** `band_for_lead(lead_h,
fitted_leads)` and `is_extrapolated_lead(lead_h, fitted_leads)` live in **`forecast/contract.py`**
(pure, stdlib, leaf) and are imported by `weights.py` and `build.py`. Two copies would let the
builder and the validator agree on a shared mistake silently; one copy plus a **table-as-test-data**
unit test (the §7 rows written out literally in the test file, not in the code) is the stronger
arrangement. `contract.py` staying the leaf is also why it may not import `weights.py`.

**Decision D-F3-B — the rule-8 universe is derived from `meta` alone.** `range(step_h, horizon_h+1,
step_h)`. The validator therefore needs no F2 import and stays stdlib-only, and truncation is
expressed exactly as F2 shipped it (trailing truncation lowers `horizon_h`; interior holes are gaps
*inside* it). Steps above `horizon_h` are neither rows nor gaps.

**Decision D-F3-C — rounding (settled, session log OQ1).** Members are stored **rounded to 4 dp**;
`blend_f` is computed **from those stored member values** and serialized **unrounded**;
`member_spread_f` = `max − min` of the stored members, unrounded. Display rounding is F5's.
The §9 *example* (`.5·78.20 + .1·78.05 + .4·78.71 = 78.389`, example prints `78.41`) violates §9
*rule 6*. **Rule 6 wins over an illustrative example.** `docs/FORECAST-SPEC.md` is NOT edited
(§14 forbids it) — the discrepancy is recorded in the F3 SUMMARY.

**Decision D-F3-D — no `truncated` key** (session log OQ3). §9's key sets are locked and exact;
adding a key is itself a contract violation. F2's internal `truncated` / `grid_max_lead_h` do not
enter the document. F1's design derives the banner from `meta.horizon_h` and `gaps[]`.

**Decision D-F3-E — `member_spread_f` is validated** (session log OQ2), within 1e-6, on the same
footing as `blend_f`. A derived field left unvalidated is a place a fabricated number can live.

**Decision D-F3-F — `_iso` is imported, not re-typed.** `build.py` uses `forecast.live._iso` and
`fetch.grib._as_utc` / `valid_time`. F2's one real defect was a second serializer disagreeing with
the first about microseconds; F3 will not add a third. `contract.py` keeps its own `_utc_stamp`
*validator* (a different job: checking a string, not producing one) mirrored from
`backend/contract.py`.

## Key Decisions

- **D-F3-A** One banding implementation, in `contract.py`; the §7 table is pinned as *test data*,
  not duplicated as code. Two copies would let builder and validator share a mistake silently.
- **D-F3-B** The rule-8 universe is `range(step_h, horizon_h+1, step_h)` derived from `meta` alone,
  which keeps `contract.py` stdlib-only and encodes F2's trailing-truncation semantics exactly.
- **D-F3-C** Rounding: members to 4 dp, `blend_f` computed from the stored members and serialized
  unrounded, `member_spread_f` likewise. §9 rule 6 then holds **by construction rather than by
  luck**. The §9 example violates the §9 rule; the rule wins.
- **D-F3-D** No `truncated` key. The key sets are locked; adding one is itself a violation.
- **D-F3-E** `member_spread_f` is validated. An unvalidated derived field is a place a fabricated
  number can live.
- **D-F3-F** `_iso` / `_as_utc` are imported, never re-typed — F2's one real defect was two
  serializers disagreeing about microseconds.
- **D-F3-G** The fixture must carry a gap **and** an extrapolated row, because F2's live run was
  64/64 clean and those branches have never met a real 404.
- **D-F3-H** T29's wording constraint is satisfied by rephrasing F3's messages
  ("weights are never rescaled over a subset of models"), **never** by editing the guard.

## Notes for Implementer

1. **`doc["results"]["6"]`, not `doc["6"]`.** The research doc's `results["<lead>"]` shorthand is
   wrong about the nesting. `lead_times` holds **integers**; the `results` keys are **strings**.
2. **`winner` has no `mae_in_sample`.** Its keys are exactly `{label, mae_out_of_sample,
   improvement_pct_vs_best_single}`. `blend_mae_in_sample` comes from the label-matched `blends[]`
   entry.
3. **The look-ahead trap, measured.** `blends[]` is sorted by *out-of-sample* MAE; the fitted winner
   sits at rank **5 / 23 / 5**. `blends[0]` is `HRRR 70/NBM 30`, `HRRR 30/NAM 40/NBM 30`,
   `HRRR 40/NAM 30/NBM 30` — a different vector at **all three** leads, and shipping it would be
   invisible in the output. Match on `winner.label`. Always.
4. **Labels omit zero-weight models** (`"HRRR 50 / NAM 10 / NBM 40"` — GFS never appears; a pure
   corner is `"HRRR only"`). Do not parse labels to recover weights; use the matched blend's
   `weights` object.
5. **`GAP_REASON` is `"absent from archive"`**, not §9's illustrative `"beyond model horizon"`.
   Both are legitimate; validate as a non-empty string and **do not pin the literal**.
6. **`improvement_pct` may be zero or negative** and must pass through honestly (§15). The
   validator must never demand a win.
7. **`fetch/grib.py` is correct and must not be "fixed":** `GRIB_shortName` is `"2t"` on valid data.
   F3 touches no GRIB anyway, but T29 will fail the suite if the wrong form appears.
8. **Do not add an `--init` flag** to `refresh.py`. Hunting a cycle that produces a nicer number is
   exactly the tuning §15 bans; F2 declined the same thing and that was the right call.
9. **An empty forecast array is a failure, not a success** (SPEC §10 — "an empty join scores
   perfectly and is fake"). `CycleResult.__post_init__` already refuses an empty record set; the
   validator refuses an empty `forecast`.
10. **Escalation clause:** if a required guard message genuinely cannot be phrased without a T29
    banned token, **STOP and escalate to the orchestrator**. Do not edit, narrow or weaken
    `tests/test_live_guards.py` — that is the "guard teaches the next agent to delete guards"
    failure F2 explicitly called out.
