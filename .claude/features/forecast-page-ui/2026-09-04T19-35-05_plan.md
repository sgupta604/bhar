## Architecture

### Summary

Three new files, no build step, no framework, no imports. `forecast.html` is a **complete static
skeleton** — every state's markup unconditionally present — that links four stylesheets in a
cascade-critical order behind an inline pre-hydration theme script. `forecast.css` re-authors the
Clarity component classes (`app.css` is off-limits) and pastes design-target §2's strip block and
§3's stale block verbatim. `forecast.js` is a single-pass renderer: fetch → merge `forecast[]` and
`gaps[]` into one `n_steps` grid → render → set `<html>` state attributes. State is **attribute-gated
on `<html>`**, never a JS `display` toggle, so any state is reproducible from devtools with no payload.

The page must render **two payloads correctly** — the live `data/forecast.json` and the deliberately
hostile `data/forecast.fixture.json` — and they disagree on every value a shortcut would hardcode.

### The three things that are read, never recomputed

`weights_fitted_at_lead_h` (the band), `is_extrapolated_lead` (the boundary), `is_stale` (the stale
treatment). All three are contract-validated server-side. A client recomputation is a second source
of truth that can disagree with the pixels.

### Why `forecast.js` stays one file

The BANLIST gate's haystack assertion is **exactly three non-empty files**. Splitting the renderer
into a fourth file (`forecast-strip.js`) would be the obvious refactor and would silently change the
gate's arity. Three files, one JS stream, no module boundary. This is a decision, not an oversight.

## Key Decisions

- **D1 — Dark mode: mirror ~25 lines, author nothing else.** `tokens.css:236-281` carries **both**
  halves of design-target §5 — the semantic override (§5.1) and the `--model-*` 500→300 step (§5.3) —
  verbatim-identical, and it is on the permitted-link list. Authoring either again would be a *third*
  declaration of the model map that §0.1 spends a section forbidding. §5.4's "ship light-only" is
  obsolete: its premise was that dark was unplanned work, and it is now free.
- **D2 — No `<script src="theme.js">`.** §3's read-only grant names three **CSS** files; §7 says import
  from them never. `theme.js`'s `linkify()` is dead here (no nav link) and its `onChange` exists to
  drive `models.js.resetColors()` — which F5 sidesteps by keeping model colours as `var(--model-*)`
  **references** in `--mark-color`. Mitigation for the duplicated key: a test asserts the
  `'internal-portal:theme'` literal is byte-identical in `forecast.js` and `theme.js`.
- **D3 — The fixture is loaded by swapping `data/forecast.json`, never by a query parameter.** A
  `?fixture=` param would ship a code path whose only purpose is loading fabricated data into a page
  whose entire value is that its numbers are trustworthy. **New at plan time:** the live payload is
  gitignored *and untracked*, so git cannot restore it — hence Task 1.2's trap-restoring script rather
  than a bare `cp`.
- **D4 — The BANLIST gate is a pytest with three proofs, not a shell one-liner.** F1's gate strips a
  BANLIST block, so its unstripped file has hits and it self-proves. `forecast.*` has no such block
  and zero banned strings by design, so the gate is structurally incapable of self-proving. Hence the
  haystack assertion, the positive controls, and the negative control. Converting it to a pytest also
  makes it run on every future ticket — which both the `forecast-api` and `demo-overview`
  retrospectives say was the missing piece.
- **D5 — `forecast.html` is authored complete and static in the foundation stream.** Design-target §3's
  own rule ("the markup is always present; visibility is an attribute on `<html>`") makes this the
  natural contract boundary: it lets Streams 2 and 3 run in parallel with zero file contention, and it
  is what makes every state reproducible from devtools with no payload.
- **D6 — `forecast.js` stays one file.** Splitting the renderer out would silently change the BANLIST
  gate's arity from three files to four.
