## 0. Read this before writing a line of code

Three sentences that decide whether this ticket is science or fiction:

1. **`models[].mae/rmse/bias` are TEST-SPLIT (out-of-sample) numbers.** Not whole-window. `contract.py`'s
   corner-agreement check forces this, and "MAE per model" reads like a whole-window number. This is the
   single easiest fatal mistake in the ticket.
2. **The one-hot identity is compared bit-exactly across two independent code paths.** `1.0*x + 0.0*y` is
   exact in IEEE-754. A tolerance here would hide precisely the bug the test exists to catch.
3. **Report what the data says.** NBM winning outright is a likely and acceptable result. If no blend beats
   the best single model, the page says so, and we ship it. See §Integrity below — it is not a preference.

## Architecture

### Summary
Five pure modules under `score/` (join, metrics, blend, split, build) plus one thin I/O entry point
(`score/run.py`), mirroring `fetch/`'s shape: functions take DataFrames in and return dicts out; only
`run.py` reads parquet or writes JSON. The pipeline joins T4's 1440 forecast rows to 932 real METAR
observations under SPEC §4's ±30 min nearest rule, keeps only valid times every included model has,
splits chronologically at (first paired valid_time + 20 days), scores MAE/RMSE/bias per model and over all
286 simplex weight vectors per lead, assembles the SPEC §7 document, and self-validates it through
`backend.contract.validate_results()` **before** writing `data/results.json` — so an invalid document can
never reach disk and the 16:00 demo can never serve one.

## Integrity — SPEC §10, in plain language, for whoever implements this

These are **integrity rules, not preferences.** SPEC §9 hard-stop #3 makes violating them a stop-and-wait,
not a judgement call.

- **Report what the data says.** NBM already *is* NOAA's blend. **NBM winning outright is a likely and
  fully acceptable result** and ships exactly as computed. If no blend beats the best single model, the page
  says so — that is a real finding ("you did not need to know in advance which model to trust"), not a
  failure of this ticket.
- **Never tune the experiment to produce a win.** Do not add lead times. Do not change the 30-day window.
  Do not try another split. Do not change the site. Do not widen the ±30 min join tolerance. Do not relax
  or delete the 80% matched-rows guard, and do not add a tolerance to the one-hot test, **to get a green
  run**. "How many variations did you try?" is the first question from the room, and the honest answer must
  be "one."
- **The research names the temptation to retune if NBM wins outright as a top risk.** Naming it is the
  mitigation: when the result comes back and the blend loses, the correct action is to write the number
  down and move to T6. Nothing in this plan is contingent on the blend winning. `contract.py` deliberately
  imposes **no sign constraint** on `improvement_pct_vs_best_single`, and T3's frontend already renders a
  negative improvement in the danger tone — both were built on the assumption this might be a loss.
- **The out-of-sample number is the headline.** In-sample sits beside it, labelled.
- **If a metric looks too good, investigate — do not ship.** Sub-1 °F MAE, a 0.0 mean offset, or an
  improvement above ~10% are reasons to re-derive, not to celebrate.
- **Join diagnostics and any excluded model are displayed, not buried.**

## Key Decisions

- **D1 — Split boundary = first paired `valid_time` + 20 days** (not day-normalised). Verified in research:
  exactly 80/40 at all three leads, matching SPEC §7's own example. Normalised gives 78/42, 77/43, 79/41.
  Split on valid_time, not init_time.
- **D2 — `models[]` metrics are TEST-SPLIT numbers.** Forced by `contract.py`'s corner-agreement check.
  Stated loudly because "MAE per model" reads like a whole-window number. Top risk.
- **D3 — Coverage is read from `data/coverage.json`, never recomputed.** T4 owns it. The 90% floor applies to
  the overall per-model value; `models[].coverage_pct` is the per-(model, lead) value.
- **D4 — The one-hot identity is verified by two independent code paths**, bit-exactly, pre-rounding, both in
  pytest (with a negative control) and as a runtime `raise` in `score/build.py` on the real numbers. If
  `models[].mae` were copied from the corner, the contract check would pass trivially and the
  NON-NEGOTIABLE test would be testing nothing.
- **D5 — One `_round()` helper (4 dp)** applied identically to `models[]` and the corner blend, so the
  contract's 1e-9 agreement survives serialisation. Rounding after the unrounded assert, never instead of it.
- **D6 — `blend_label`/`simplex_grid` are re-implemented in `score/`** with a 286-vector parity test against
  `backend.make_fixture`. `make_fixture` is the *fake-data* generator; importing it into the real pipeline
  would couple the science to it.
- **D7 — Deterministic tie-breaks:** blend sort key `(mae_out_of_sample, grid_index)`; in-sample argmin
  tie-break lowest `grid_index`.
- **D8 — `meta.window`** = min/max paired valid_time across included models; `days: 30`.
- **D9 — The exclusion path is tested with synthetic 3-/2-model inputs** (grids 66/11), never by dropping a
  real model. All four are at 100%; manufacturing an exclusion would be tuning the experiment.
- **D10 — Vectorised `P @ W.T`** with an explicit column-order `raise` in production code. 286 loops removed,
  and with them 286 chances to mis-index a model column.
- **D11 (new) — Atomic write + proven rollback before any code is written.** `data/results.json` is the demo
  insurance artifact; a failed T5 must not leave the 16:00 demo with nothing.
- **D12 (new) — The winner rule is in-sample argmin, and `blends[0]` is explicitly rejected**, while
  `best_single_model` is the lowest **out-of-sample** corner. The baseline gets hindsight; the blend does
  not. This asymmetry is deliberate, enforced by `contract.py`, and makes a negative improvement possible —
  which is what makes a positive one meaningful.

## Notes for Implementer

- **The parquet's `model` column is lowercase** (`gfs/hrrr/nam/nbm`); the JSON's must be uppercase
  (`HRRR, GFS, NAM, NBM`) in canonical order. Map once, in one place, and `raise` if the map is not total.
  Lowercase leaking into the JSON breaks the frontend's model list.
- **Sort the left frame by `valid_time` ONLY.** `sort_values(["model","valid_time"])` looks sorted, passes
  `merge_asof`'s own check in some shapes, and is wrong.
- **The right join key is consumed** by `merge_asof` — carry the obs timestamp as its own `obs_time` column
  or you cannot compute `offset_min` at all.
- **No `by=` argument** on the merge. Observations are one global series.
- Both time columns are `datetime64[us, UTC]` and `model` is plain `pa.string()` (never a pyarrow dictionary
  / pandas Categorical) — T4 verified this on round-trip specifically because a dictionary dtype silently
  breaks join-key comparison.
- **Explicit `raise`, never bare `assert`, in all pipeline code.** `python -O` strips asserts, and these
  guards are the only thing between the demo and a fabricated number. `contract.py`'s docstring states this
  rule; mirror its style — a message that names the offending path/model/lead and both values.
- Expected real diagnostics (from the research dry run — use them as a tripwire, not a target):
  **480/480 matched = 100.00% at every lead**, mean abs offset **7.92 min**, max **8.0**, offsets `−8` for
  ~97% of rows plus a few `+1/+6/+7` from SPECIs, **120/120** paired valid times, **80/40** split.
  A materially different number means something changed — investigate before shipping.
- The last forecast valid time `2026-09-04T00:00Z` matches obs `2026-09-03T23:52Z` at 8 min — inside
  tolerance. Nothing is lost at the window edge.
- **`results` keys are strings** (`"6"`, not `6`). `contract.py` fails loudly on this, but only after you've
  wasted a run.
- T3's frontend finds the winner row **by `winner.label`, never by index** — the fixture's winner sat at OOS
  rank #17 at 24h. Labels must be unique across all 286 blends.
- The 16:00 demo command (T3, verbatim, because port 8000 is squatted by a VS Code helper that answers
  `/health` identically): `BHAR_BACKEND_PORT=8011 BHAR_FRONTEND_PORT=5184 ./run.sh`. Confirm identity via
  `/openapi.json`'s title, **never** `/health`.
- A fresh clone has **no parquet data** (gitignored) — `score.run` must fail with a clear message if the
  parquets are missing, not with a bare `FileNotFoundError` traceback.
