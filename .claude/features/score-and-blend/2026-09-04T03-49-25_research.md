# Research: score-and-blend (T5 of 6 — the scientific core)

**Date:** 2026-09-04T03:49:25 local (08:49:25Z) | **Status:** research-complete

## Goal

Join T4's real forecasts to real METAR observations under SPEC §4's ±30 min nearest rule, score
MAE/RMSE/bias per model per lead, search the full 286-point weight simplex on a 20/10 chronological
split, and write a real `data/results.json` that passes `backend/contract.py::validate_results()`
unchanged with `is_synthetic: false`. No frontend or backend edits.

## Contract facts that constrain the math (read out of `backend/contract.py`)

These are not optional style points; each one fails the run loudly if violated.

| `contract.py` rule | Consequence for T5 |
|---|---|
| `models[i].mae` must equal that model's one-hot `mae_out_of_sample` within `1e-9` (line ~`corner_mae` check) | **`models[]` MAE/RMSE/bias are the TEST-split (out-of-sample) numbers**, not whole-window numbers. Easy to get wrong. |
| `len(blends) == comb(10+n-1, n-1)` | 286 for 4 models, 66 for 3, 11 for 2 — automatic once exclusions are honoured. |
| `blends` sorted by `mae_out_of_sample` ascending, `rank == i+1`, vectors unique, every corner present | Deterministic tie-break needed: sort key `(mae_out_of_sample, grid_index)`. |
| `winner`'s blend must be the **in-sample argmin** | Winner is chosen on train, never on test. |
| `best_single_model` must be the **lowest OOS** corner | Baseline gets hindsight; the blend does not. This asymmetry is the honest framing and is enforced. |
| `improvement == (best_single − winner)/best_single × 100` within 0.05 pp, **no sign constraint** | Emit the signed value; never clamp. |
| `models[]` order must equal `meta.models_included` | Emit in canonical order. |
| `n_samples.train/test` must be positive ints; `matched_pct` in [0,100] | Real numbers, 80/40 and 100.0. |

## The join — exact `merge_asof` specification

```python
obs = obs.dropna(subset=["temp_f"]).sort_values("valid_time")          # right frame
obs = obs.rename(columns={"valid_time": "obs_time", "temp_f": "obs_f"})
fc  = forecasts.sort_values("valid_time")                              # left frame, GLOBAL sort
m = pd.merge_asof(
        fc, obs,
        left_on="valid_time", right_on="obs_time",
        direction="nearest",
        tolerance=pd.Timedelta(minutes=30),
        allow_exact_matches=True,       # default; an exact hit is the best match
    )
m["offset_min"] = (m["obs_time"] - m["valid_time"]).dt.total_seconds() / 60.0
```

Non-obvious requirements, each a place a subtle bug produces confident fake numbers:
- **Both frames must be sorted ascending on the join key** — `merge_asof` raises otherwise, but a
  per-model `sort_values(["model","valid_time"])` looks sorted and is not. Sort by `valid_time` only.
- **No `by=` argument.** Observations are a single global series; grouping by model is unnecessary
  and would silently change nothing here while inviting a future bug.
- **Both keys must be tz-aware and the same dtype** — both are `datetime64[us, UTC]`. A tz-naive
  side raises; a mixed-resolution side can coerce.
- **The right key is consumed**, so the obs timestamp must be carried as its own column
  (`obs_time`) to compute `offset_min` at all.
- **NaN keys are illegal**; obs is already `M`-dropped by T4 — re-drop defensively anyway.
- **Duplicate obs timestamps would make the "nearest" pick order-dependent** — T4 verified there
  are none; assert it rather than trust it.
- Unmatched rows come back with `obs_f` NaN — count them for `matched_pct`, then drop them.
- **Behaviour to pin with a test, not assume:** which side `direction="nearest"` picks on an exact
  ±equidistant tie, and whether `tolerance` is inclusive at exactly 30 min. Write the test, record
  the observed behaviour; do not guess in the plan.

## Decisions taken (user asleep — no open questions)

| # | Decision | Rationale |
|---|---|---|
| **D1** | **Split boundary = (first paired `valid_time` for that lead) + 20 days**, train = `< boundary`, test = `>= boundary` | Verified: yields **exactly 80/40 at all three leads**, matching SPEC §7's own example. A `.normalize()`d day boundary gives 78/42, 77/43, 79/41 — same idea, worse fit to the spec. Split on **valid_time**, not init_time, because the paired sample is keyed on valid time. |
| **D2** | `models[]` metrics (`mae`/`rmse`/`bias`) are computed on the **test split** | Forced by `contract.py`'s corner-agreement check. Stated loudly because "MAE per model" reads like a whole-window number. |
| **D3** | `models[].coverage_pct` is read from `data/coverage.json`'s **per-(model, lead)** value; the 90% floor is applied to the **overall per-model** `coverage_pct` | T4 owns coverage; T5 must not recompute it (SPEC §8 T4/T5 split, and T4's own "T4 flags; T5 decides"). |
| **D4** | The one-hot identity is verified by **two independent code paths** — `metrics.model_metrics()` vs `blend.blend_metrics(one_hot)` — compared **before rounding**, both in pytest and as a runtime `raise` in the pipeline | If `models[].mae` were simply copied from the corner, the contract check would pass trivially and the NON-NEGOTIABLE test would be testing nothing. |
| **D5** | All emitted floats pass through one `_round()` helper (4 dp) applied to both the corner blend and `models[]` | Guarantees the contract's `1e-9` corner agreement survives serialisation. Rounding after an unrounded equality assert, never instead of it. |
| **D6** | `blend_label` / `simplex_grid` are re-implemented in `score/` with a **parity test** against `backend.make_fixture` over all 286 vectors | `make_fixture` is the synthetic-fixture generator; importing it into the real pipeline couples the science to the fake-data module. A parity test gets the guarantee without the coupling and without touching GREEN T3 code. |
| **D7** | Blend sort tie-break = `(mae_out_of_sample, grid_index)`; in-sample argmin tie-break = lowest `grid_index` | Deterministic reruns; `contract.py` demands a strict rank ordering. |
| **D8** | `meta.window.start/end` = min/max paired `valid_time` across included models; `days = 30` | Honest and derived from the data actually scored. `init_runs` from SPEC §3. |
| **D9** | Excluded-model code path is exercised by **unit tests with a synthetic 3-model and 2-model coverage input** (grid 66 / 11), not by dropping a real model | T4 reports 100% for all four, so no real exclusion exists. The path must exist and be tested; manufacturing one would be tuning the experiment. |
| **D10** | Blend evaluation is vectorised: pivot to a `(n_valid × n_models)` matrix `P`, weights `(286 × n_models)` matrix `W`, `preds = P @ W.T` | 286 × 3 leads × 120 rows is trivial; one matmul removes 286 Python loops and the per-loop chance of a mis-indexed model column. |

## Patterns to follow (from GREEN code)

- **`backend/contract.py`** — explicit `raise` with the offending JSON path in the message; module
  docstring states *why* each rule exists. Mirror this in `score/`'s guards.
- **`fetch/schema.py::write_parquet_checked`** — the "anti-fake" assert centralised in the writer.
  T5's analogue: validate against `validate_results()` **before** writing `data/results.json`, so a
  contract violation never reaches disk.
- **`fetch/backfill.py`** — pure functions over a ledger, unit-testable offline with no network.
  Mirror: `score/` functions take DataFrames in, return dicts out; only `score/run.py` does I/O.
- **T4's progress doc** — a "too-clean result" is checked, not accepted. 100% join match is exactly
  that shape and must be defended in the implementation write-up.
- **`backend/make_fixture.py`** — canonical `MODELS` tuple, label rule, grid-size self-check.

## Patterns to avoid

- Any `assert` statement in pipeline code (`python -O` strips it).
- Recomputing coverage — T4 owns it; two sources of truth will disagree at 16:00.
- Selecting the winner as `blends[0]` (OOS rank 1). That makes a win true by construction and
  `contract.py` rejects it.
- Client-style arithmetic on error values: every number the page shows must exist in `results.json`.
- Reindexing/resampling observations to the hour, or `fillna`/`interpolate` anywhere near obs.
- Adding a field to `meta` (elevation delta, extra diagnostics) — `_exact_keys` rejects it.
- Lowercase model names leaking into the JSON.

## Integrity — SPEC §10, stated plainly for the implementer

- **Report what the data says.** If no blend beats the best single model, the page says so.
  **NBM winning outright is a likely and acceptable outcome** and ships as-is.
- **Never tune the experiment to produce a win.** Do not add lead times, change the window, change
  the split, change the site, widen the ±30 min tolerance, or relax the 80% assert to get a green
  run. §9 hard-stop #3 makes this a stop-and-wait, not a judgement call.
- **The out-of-sample number is the headline**; in-sample is shown beside it, labelled.
- **If a metric looks too good, investigate — do not ship.** A sub-1 °F MAE, a 100% match with a
  0.0 mean offset, or an improvement above ~10% are all reasons to re-derive, not to celebrate.
- Join diagnostics and any excluded model are displayed, not buried.

## The NON-NEGOTIABLE test — exactly how it is written

`tests/test_blend.py::test_one_hot_reproduces_pure_model_metrics`

1. Build a **synthetic** joined frame (no parquet, no network): ~40 valid times × 4 models × obs,
   with deliberately different per-model error signatures (different bias signs and spreads) so a
   column mix-up cannot pass by coincidence.
2. For each model `m`, each lead, and each split (`train`, `test`):
   - `a = metrics.model_metrics(frame, m)` → `(mae, rmse, bias)` — the per-model path.
   - `b = blend.blend_metrics(frame, weights=one_hot(m))` → `(mae, rmse, bias)` — the blend path.
   - Assert `a == b` **exactly** (`abs(a-b) == 0.0`, tolerance `1e-12` at most). `1.0*x + 0.0*y +
     0.0*z + 0.0*w` is bit-exact in IEEE-754, so exact equality is the right assertion — a
     tolerance here would hide the bug the test exists to catch.
   - Assert on **all three metrics**, not just MAE.
3. A **negative control**: the same assertion with a deliberately permuted weight vector must
   **fail** — proving the test can fail. (A test that cannot fail is the §10 failure class in
   miniature.)
4. **Runtime guard** in `score/build.py`: before emitting each lead, `raise` if any
   `models[m].mae` and model `m`'s one-hot `mae_out_of_sample` differ by more than `1e-9`
   **pre-rounding**. Same check, in production, on the real numbers.

Supporting pure-logic tests (§13): `merge_asof` join against a synthetic off-hour fixture
(match at 8 min, no match at 31 min, tie behaviour pinned, `offset_min` sign and value);
the 80% guard **fires** on a deliberately sparse fixture and does **not** fire at 100%;
hand-computed MAE/RMSE/bias known answers; simplex grid = 286/66/11 and sums to 1.0;
`blend_label` parity with `backend.make_fixture`; split boundary yields 80/40 on a synthetic
120-point series; pairing drops a valid_time when one model is missing.

## Recommended approach

Five small pure modules under `score/` plus a thin `run.py` that owns all I/O, mirroring `fetch/`'s
shape. Build the join first with its guard and diagnostics, then metrics, then the vectorised
286-vector grid, then the split, then the document assembler that self-validates through
`backend.contract.validate_results()` before writing — so an invalid document can never reach disk
and the demo can never serve one. The one-hot identity is enforced twice: as a two-path pytest on
synthetic data with a negative control, and as a pre-rounding runtime `raise` on the real numbers.
Everything the plan needs is already measured: 100% join, 7.92 min mean offset, 80/40 splits, no
exclusions.

## Scope: **M**

~700 lines of implementation and tests, no new dependencies, no network, no UI, seconds of compute.
The size is in the guards and the test matrix (4 models × 3 leads × 2 splits × 3 metrics), not in
the algorithm. Contract and inputs are both locked and verified, which removes the usual unknowns.

**Defer to T6 (README), not here:** the grid-cell vs station elevation delta (`meta` keys are
locked and cannot carry it), the "120 samples are not 120 independent observations" caveat, and the
no-bias-correction rationale.
