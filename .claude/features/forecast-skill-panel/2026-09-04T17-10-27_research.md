## The one thing that decides how realized-vs-backtest is presented

**The 32 archived days are not the 10 test days.** The 120 rows per lead are the full paired series
— the same 80 train + 40 test the backtest split. So `1.8253` and `1.9173` are **numbers over
different sets of days**, and `1.8253` is lower *because it includes the fitted days*, where the
blend is 1.7792. Putting them side by side unlabelled would read as "it's doing better than
advertised", which is a claim about the future by implication.

**Verified cross-check (a test, not a display).** Re-splitting the history entries **per lead** at
`first paired valid_time for that lead + 20 days` reproduces the published backtest:

| Lead | boundary | train n / MAE | published in-sample | test n / MAE | published OOS |
|---|---|---|---|---|---|
| 6 h | 2026-08-24T12:00Z | 80 / 1.7792 | 1.7793 | 40 / 1.9172 | 1.9173 |
| 12 h | 2026-08-24T18:00Z | 80 / 1.9730 | 1.9730 | 40 / 1.9677 | 1.9661 |
| 24 h | 2026-08-25T06:00Z | 80 / 2.0150 | 2.0141 | 40 / 2.1065 | 2.1066 |

(The residual differences are `blend_f`/`observed_f` rounding in the history JSON. A **global**
boundary — first valid time across all leads — gives 79/41 and 77/43 and does **not** reproduce it;
the boundary is per-lead.)

**Recommendation:** use this as a **pytest cross-check** that F6's replay and F3's skill block
describe the same days. Do **not** render a frontend-recomputed split: it is "computing new
metrics" (an explicit F7 non-goal), and it would put two slightly different "out-of-sample" numbers
(1.9677 vs 1.9661) on the same page, which is worse than one.

## Contract

**No contract change is needed.** Everything F7 renders is already in the two payloads:

- skill numbers → `skill.by_lead[]` (all six fields).
- window/split/age/leads/path → `meta.weights_source`.
- fitted weight vector per lead → derived from the forward rows: the `weights` of any row whose
  `weights_fitted_at_lead_h` equals that lead. (`meta.weights_by_lead` in the *history* payload is a
  cross-check, not the forward page's source.)
- realized errors → `history.days[].mae_f` and `days[].entries[].error_f` / `lead_h`.
- day count → `history.days.length`; join provenance → `history.meta.join`.

Edge case, handled without a contract change: if a truncated horizon leaves **no** forward row
mapped to a fitted lead, that lead's `.skill-weights` chips are **omitted entirely** — never
substituted from the history payload, never renormalized, never invented (see OQ2).

- **Guard-module shape** — `tests/test_forecast_history_ui_guards.py` is the model: import

  `region_from_marker`-style helper that **raises** when the marker is gone.
- **Every guard carries a positive control and a haystack assertion.** This project has shipped
  three guards that could not fail. `test_forecast_ui_guards.py` PROOFs 1-4 and
  `test_forecast_history_ui_guards.py` PROOFs 1-5 are the required shape.
- **Never type a banned token in a test file** — assemble it from character escapes

- **Payload-derived everything.** `forecast.js`'s own header states the rule; `renderNote()`
  (`:783`) and `renderLeadsNote()` (`:990`) are the worked examples of composing prose from payload
  fields including a count word.
- **Comment-stripped scanning**, so a comment that *forbids* a shape is not counted as a violation

- **`--warn` for limits, `--danger` for fabrication, no `--success` in this panel.**

## Patterns to avoid

- Hardcoding `HRRR`, `KOMA`, `Omaha Eppley Airfield`, `6/12/24`, `30`, `120`, `40` — all are guard
  failures **and** all are wrong on the fixture.
- Sorting the lead blocks or the `.skill-nums` cells by magnitude. Sorting by MAE is the §15 tuning
  ban in another costume, and it is what would make the 12 h ordering unreadable.
- Rendering a delta between OOS and in-sample as a tone-coloured or arrowed figure. At 12 h it would
  favour the fit, and a green arrow there asserts what README C1 says the data does not support.
- Looking a skill entry up by `weights_fitted_at_lead_h`. That field is `24` for a 42 h row, so
  indexing skill by it would show the 24 h MAE on an extrapolated cell — the interpolation §7 bans,
  arriving through a lookup instead of an arithmetic.
- Any spread shape (`band|ribbon|envelope|whisker`) — F6's guard already scans for these
  case-insensitively as substrings; a class named `skill-error-band` fails.
- Re-deriving the D4 improvement-state table instead of reading
  `.claude/features/demo-shell/design-target.md` §3.
- `Math.abs`, clamping, or a CSS `::before` sign on `improvement_pct`.

## The guard question — how to make "no probability, no promise" mechanically checkable

**The gap is real.** F5's BANLIST catches eleven banned *identifiers* plus U+00B1. It would pass a
panel that said "we expect tomorrow to be within 2 degrees". And there is **no JS test runner in
this project by design** (SPEC §13: pure-logic pytest, no live network), so no guard can read the
rendered DOM. Any honest guard here is a **source-level** guard, and that is its ceiling.

**Recommended: a four-layer guard, in `tests/test_forecast_skill_panel_copy.py`.**

**Layer 1 — containment (this is what makes the other three mean anything).**
All panel prose lives in one delimited constant block in `forecast.js`:
`/* ══ PANEL COPY — pinned by tests/test_forecast_skill_panel_copy.py ══ */ … /* ══ END PANEL COPY ══ */`.
Tests: the block extracts (raising if the marker is gone), clears a byte floor, and — the key
assertion — **no string literal longer than ~40 chars exists in the F7 region outside that block**.
Without containment, layers 2-4 scan a subset of the copy and report the same green as a full scan.

**Layer 2 — pinned copy (primary).** The three lead templates, the basis sentence, the extrapolated
sentence, the cross-link and the realized sentence are asserted **byte-for-byte** against strings
pinned in the test. §6 copy then cannot change without a test change and a human reading the diff.

**Layer 3 — claims blacklist with a sanctioned-phrase allowlist (secondary).** A regex over the copy
block for: `will\s+(be|have|stay)`, `going to`, `\bexpect`, `\bpredict`, `\banticipate`,
`accurate to`, `within \d`, `margin of error`, `plus or minus`, `give or take`, `\bchance\b`,
`\bodds\b`, `\blikely\b`, `\bconfiden`, `\bguarantee`, `\bpromis`, `\bshould be\b`, `\btypically within\b`.
**The negation problem is why this needs the allowlist, not a plain blacklist:** the required copy
legitimately contains *"not a promise about this forecast"* and *"has no claim on winter
inversions"*. So the rule is: **every hit must appear verbatim in a pinned `SANCTIONED` tuple**
(`not a promise about this forecast`, `has no claim on`). An unsanctioned hit fails. Adding a new
promise-shaped phrase therefore requires editing the allowlist — a visible, deliberate act.

**Layer 4 — required markers per lead sentence (structural).** Each lead template must contain, in
source: `Over the last`, `' was '`, an in-sample clause containing `In-sample`, the sample clause
containing `independent days, not`, and the closer `That is history, not a promise about this
forecast.` Plus a digit scan proving `.skill-extrapolated` and its region contain **no digit other
than the two in `24-hour`**.

Every layer gets a positive control: inject a violating string into an in-memory copy and assert
red, through the same code path (F6's PROOF 3 shape).

**Bonus, in scope and worth doing:** run Layer 3's pattern over the **server-authored** values
`skill.basis` and `skill.note` in `data/forecast.json` and `data/forecast.fixture.json`, read-only.
`forecast/contract.py` sweeps banned *names* (`_sweep_banned_names`, `:426`) but validates
`skill.note` only as a non-empty string (`_text`, `:927`) — **no value-level ban exists anywhere**.
A bad `note` would render verbatim into `.skill-basis` and nothing would catch it. A test can close
this without touching `forecast/`.

**What this cannot catch — say so in the plan, do not overclaim:**
1. It never reads the rendered DOM. Correct source + broken render still passes. Mitigation: an
   `agent-browser` snapshot as evidence only, **never blocking** (SPEC §13, §11 R5).
2. It cannot catch a claim phrased in words nobody blacklisted ("we'd be surprised by more than two
   degrees"). Layer 2's byte-pinning is the real defence; layer 3 is a tripwire for drift.
3. It cannot police what the **server** sends in future payloads — only the two committed ones.
4. It cannot see CSS `content:` copy unless the F7 region in `forecast.css` is scanned too — so

## Recommended approach

Extend the three existing files only. `renderSkillShell` already owns the panel's provenance half;
add three sibling renderers beside it — `renderSkillLeads` (iterating `skill.by_lead`),
`renderSkillBasis`, `renderSkillRealized` (guarded on `state.history`, re-run from both fetch
chains) — with every sentence composed from a single pinned copy block near the top of
`forecast.js`. Nearly all CSS is already shipped (F5 authored `.skill-*` in full); the additions are
the D4 tone hooks, the lead pill, and the realized marks. Ship two new test modules: a guard module
in F6's imported-not-retyped shape, and a copy module implementing the four-layer containment +
pinning + allowlisted-blacklist + markers scheme, every layer with a positive control, and every
acceptance test run against **both** `data/forecast.json` and `data/forecast.fixture.json` so the
−12.5 % loss and the per-lead-varying `best_single_model` are actually exercised.

## Scope: **M**

Three files, ~4 new JS functions and one class swap, a modest CSS addition on an
already-authored class set, and no contract change — that is S. The two test modules are what make
it M: the guard module must import and re-prove F5's machinery over a new region, and the copy
module is the ticket's actual deliverable, since §6 lives or dies in the copy rather than the code.
Not L: no backend, no new endpoint, no new metric, and the DOM shell already exists.
