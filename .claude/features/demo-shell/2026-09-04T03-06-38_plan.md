## Architecture

### Summary
`data/results.json` on disk is the entire system boundary. `backend/make_fixture.py` writes a
deterministic synthetic file in the SPEC §7 shape; `backend/contract.py::validate_results()` is the
executable lock on that shape; `backend/main.py` validates on load and serves the file whole at
`GET /api/results` (503 if invalid or missing — never an empty payload); the static frontend renders
every panel from that single payload, with **all interactivity done client-side by exact lookup into
the complete 286-point weight grid**. T5 later overwrites one file and edits no frontend code.

### Data Flow

```
backend/make_fixture.py  (seeded, pure, offline)
        │  writes both
        ├──────────────> data/results.synthetic.json   (durable insurance copy, never auto-served)
        └──────────────> data/results.json             ◄──── T5 OVERWRITES THIS ONE FILE
                                   │
                    backend/contract.py::validate_results()   ← same function used by T5's test
                                   │  pass → 200      fail/missing → 503 + reason
                                   v
                    backend/main.py  GET /api/results  (+ CORS, TR5)
                                   │  http://localhost:8000  (or ?api= override)
                                   v
        frontend/app.js  — ONE fetch, ONE payload, zero further network
                                   │
     ┌────────────┬────────────┬───┴────────┬─────────────┬──────────────┐
     v            v            v            v             v              v
  banner      header +     leaderboard   sliders       chart        footer
 (data-       lead-time    (rank/label/  (exact          (2-model    (signed
  synthetic)   toggle       bar/°F)      lookup into    slice,       improvement,
                                          blends[])     lookup)      source, joins)
```

**The one rule that makes the slider honest (D5):** the number under the sliders is *read out of*
`blends[]`, never computed in the browser. `blends` must therefore be the **complete 286-point grid**
(`C(13,3)` for 4 models at step 0.1), not a top-N. A truncated array silently kills the slider.

## New decisions this plan records

### D13 — Winner is selected on **in-sample**, reported **out-of-sample** (this is what makes a negative improvement possible)
`blends` is sorted by `mae_out_of_sample` ascending (SPEC §7, unchanged). The grid contains the
one-hot corners, so the OOS-minimum blend can never be worse than the best single model — meaning
if `winner` were simply `blends[0]`, `improvement_pct_vs_best_single` could **never** be negative and
D4's danger path would be unreachable and untestable.

SPEC §5 and decision-log #5 settle it: *"Fit on days 1–20, evaluate on days 21–30 … the out-of-sample
number is the headline."* Therefore:

- `winner` = the blend with the lowest **`mae_in_sample`** (the fitted choice).
- `winner.mae_out_of_sample` is that blend's test error — it may be worse than any single model.
- `improvement_pct_vs_best_single = (best_single.mae_out_of_sample − winner.mae_out_of_sample) / best_single.mae_out_of_sample × 100`, **signed**.
- **Frontend consequence, non-obvious and easy to get wrong:** the winner row is **not necessarily
  row 1** of the leaderboard (which is OOS-ordered). The UI must locate the winner row by matching
  `winner.label` (or the weight vector), **never by index 0**.
- **T5 obligation:** same selection rule. Written into the seam contract below.

### D14 — `models_excluded` is exercised with a model that is *not* in `models_included`
SPEC §7's example lists `NAM` in both `models_included` and `models_excluded` — internally
inconsistent, and copying it would break the 286 count. The fixture instead excludes a model that
was never in the study: `[{"model": "RAP", "coverage_pct": 71.2, "reason": "below 90% coverage floor"}]`.
`models_included` stays the four models → grid stays 286 → FR11's exclusion panel is still exercised.
`validate_results()` asserts the two lists are **disjoint**. This is an annotation on a free-form
list, not a shape change; T5 emits its real exclusions in the same form.

   and note the T2 state separately in the session log.

   `.venv` is the one asset whose loss costs the night (T1 retrospective).

## Key Decisions (for SUMMARY.md)

- **D1 → design-target.md, not a canvas.** A written visual target fixes the design before code at ~10 minutes' cost; a canvas costs 20–40 and returns a picture nobody awake can react to.
- **D5 → the slider is a lookup, not a calculation.** The displayed number is read out of `results.json`, so "the value agrees with the underlying data" is true by construction rather than by testing. Its cost is the constraint that `blends` must be the full 286-point grid — enforced in the validator so T5 fails loudly instead of shipping a dead slider.
- **D13 → winner picked in-sample, reported out-of-sample.** Without this, `improvement` can never be negative and SPEC §10's honesty requirement is untestable. It is also simply what SPEC §5 and decision-log #5 describe.
- **The fixture emits a negative improvement at 24h on purpose.** The dishonest-rendering path is exercised by the demo itself, not just by a test.
- **All four synthetic signals key off one boolean**, so T5's swap edits zero frontend files.
- **503 over an empty payload; no silent fallback to the synthetic copy** (D12). Refuse rather than degrade — the same principle T1 put in `run.sh`.
- **Identity is `/openapi.json`'s title, never `/health`** — the machine has a squatter on 8000 that fakes a green check.
- **Cut order fixed in advance** (pair selector → chart → dark mode) so scope can be shed at 05:30 without waking anyone.

## Notes for Implementer

- **`results` keys are strings (`"6"`), `lead_times` are ints (`6`).** `String(lead)` at every index site. Cheapest possible bug, hardest to see.
- **CORS is the blank-page bug (TR5).** Frontend `:5173` ≠ API `:8000`. Omit `CORSMiddleware` and you get chrome with no data and a console error you may not look at. Add it in the first backend edit, not the last.
- **Winner ≠ `blends[0]`** (D13). Match on `winner.label`.
- **Never `Math.abs`, never clamp** the improvement. Grep for it before committing.
- **Never interpolate** on a slider lookup miss — render `—` and warn. An interpolated number that looks plausible is the §10 failure class in miniature.
- **`--danger` is pink `#de0f80`**, not red. Data-viz pink `#f0329a` is deliberately unused for a model so nothing on the page competes with the synthetic banner or the negative-improvement signal.
- Clarity semantic tokens only, never raw scale values (token doc §1.3 rule, verbatim). Sliders and chart axes are the two gaps you design yourself — the primitives to borrow are named in token doc §5.4 and §8.5.
- `.claude/active-work/` is gitignored: the screenshot lives on disk for the 07:30 window and is not committed. That satisfies SPEC §14.4.
- T1's retrospective, worth heeding: don't stack a CLI flag that config already sets, and assume `uv run` orphans a grandchild process on kill.
- **After this ticket there must be a demoable artifact.** If a task blocks, cut per the cut order, log it, commit green, and move on (SPEC §9). Do not halt the run.
