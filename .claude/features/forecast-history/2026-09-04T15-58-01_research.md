## Verified facts about the inputs

Both parquets are symlinks into the off-limits main checkout. **Read through, never write through.**
Measured directly (`pandas.read_parquet`), not assumed:

**`data/forecasts.parquet`** — 1440 rows, 0 NaN.

| column | dtype | notes |
|---|---|---|
| `model` | `str` | **lowercase**: `gfs, hrrr, nam, nbm`. `score.blend.canonical_model_name` maps to UPPERCASE. |
| `init_time` | `datetime64[us, UTC]` | hours 0/6/12/18; `2026-08-04T06:00Z` … `2026-09-03T00:00Z` |
| `lead_h` | `int32` | **exactly {6, 12, 24}** |
| `valid_time` | `datetime64[us, UTC]` | `2026-08-04T12:00Z` … `2026-09-04T00:00Z` |
| `temp_f` | `float64` | already °F |

Exactly **120 rows per (model, lead_h)** — 4 models × 3 leads × 120 = 1440. No holes.

**`data/obs.parquet`** — 932 rows, 0 NaN, 2 columns only: `valid_time` (`datetime64[us, UTC]`),
`temp_f` (`float64`, whole degrees). **Timestamped at `:52`, not on the hour** — confirms spike F5.
Range `2026-08-04T00:52Z` … `2026-09-03T23:52Z`. Minutes seen across the file span `:00`–`:59`
(sub-hourly specials exist in the source), but the routine hourly rows the join lands on are `:52`.

**The join, dry-run through `score.join.join_forecasts_to_obs` (unmodified):**

- **1440 / 1440 matched — 100.0 % at every (model, lead).** No day falls below the 80 % floor,
  so the real data never exercises the omitted-day branch (see Risks).
- `offset_min` ∈ {−8.0, +7.0}; **every offset is a whole number of minutes**; mean |offset| =
  **7.9194 min** (matches `results.json` `join_diagnostics`: 7.925 / 7.9167 / 7.9167 per lead, and
  the design target's "7.92 minutes" copy).
- The last forecast valid time (`2026-09-04T00:00Z`) matches the `2026-09-03T23:52Z` observation at
  −8 min. Nothing is lost at the tail.

**Derived entry shape** — pivot to one row per `(valid_time, lead_h, init_time)` → **360 entries**
(120 per lead), no duplicates. Grouped by UTC date: **32 distinct dates**, not 30 — two are partial
edges (`2026-08-04`: 3 entries, leads 6 and 12 only; `2026-09-04`: 1 entry, lead 24 only;
`2026-08-05`: 11; `2026-09-03`: 9). **Nothing is omitted; every date has ≥ 1 matched entry.**

**Realized history numbers this payload will publish** (whole window, computed here as a
sanity anchor for `/test`):

| lead | n | blend MAE | blend bias | best-single (HRRR) MAE |
|---|---|---|---|---|
| 6 | 120 | 1.8253 | +0.1129 | 2.0691 |

### The §10 sketch is a sketch — the validator needs an exact key set

`_exact_keys` rejects any key not in the locked set, so `/plan` must lock one. The §10 jsonc block
uses `/* verbatim from results.json */` comments and omits things the design target's own copy
demands. **Recommended additions to `meta`, each with a named reason:**

| Added key | Why it is required, not decorative |
|---|---|
| `models_included` | The validator cannot check `members`' key set without it; §9 carries it for the same reason. |
| `weights_by_lead` `{"6": {...}, "12": {...}, "24": {...}}` | §10 entries carry **no `weights`** (unlike §9 rows), so without this the `blend_f == Σ w·m` identity that FORECAST-SPEC §18 requires as a test **cannot be checked from the document at all**. Per-lead in `meta` rather than per-entry avoids repeating 4 floats 360 times. |
| `best_single_model_by_lead` `{"6": "HRRR", …}` | The UI's `BEST SINGLE` column needs the model's **name**. Reading it from `/api/forecast` would couple the back-arrow to `data/forecast.json`, which is **gitignored** — on a fresh clone that endpoint 503s and the column would lose its label, defeating §16 R6. |
| `join` `{tolerance_min, n_forecast_rows, n_matched_rows, matched_pct, mean_abs_offset_min}` | This is **where "assert on match counts" gets published** rather than only enforced. design-target §1.6's offset note quotes "the mean absolute offset over this window was 7.92 minutes" — that number must come from the payload, not a JS literal. |
| `omitted_days` `[{date, reason, n_forecast_rows, n_matched_rows}]` | §10 says a zero-match day is "omitted **with the reason recorded**". There is nowhere else to record it. design-target §1.6 renders these below the day card with the reason string verbatim in mono. |
| `source` | `"noaa_s3_grib"` — provenance symmetry with §9. |

**Recommended addition to each day:** `n_by_lead` `{"6": 4, …}`. `2026-09-04`'s `mae_f["24"]` is a
**one-sample** mean (0.49) and `2026-08-04`'s `mae_f["12"]` is a **one-sample** mean (14.47). Shown
without its count, a one-sample daily MAE reads exactly like a four-sample one. This is the same
class of honesty the `~30 independent days, not 120` rule exists for.

**Payload precision (design-target §6, line 1826-1832) — binding:**

| value | payload | page |
|---|---|---|
| `blend_f`, `members[*]`, `observed_f`, `best_single_model_f`, `error_f` | **2 dp** | **1 dp** + ` °F` |
| `days[].mae_f` | **2 dp** | 2 dp verbatim |
| `obs_offset_min`, `lead_h` | **integer** | integer, mono; offset signed |
| `weights[*]` | 1 dp | 1 dp always — GFS renders `0.0`, never `0`, never blank |

Because the payload is rounded, the validator's identity checks are **tolerance-bounded, not
exact**: with members and `blend_f` both at 2 dp, `|blend_f − Σ w·m| ≤ 0.005 + ε`; `error_f`,
being `round(blend_f − observed_f, 2)` of two 2-dp values, is exact to ~1e-9; `mae_f` needs
`≤ 0.005 + ε`. A 0.005 window is still a real guard — a wrong weight vector moves `blend_f` by
tenths of a degree. §9's `BLEND_TOL = 1e-6` is **not** reusable here; §10 needs its own constant.

**Signed-error copy (design-target §1.6, verbatim):** `> 0` → `+1.24 °F  warm`; `< 0` →
`−0.80 °F  cold`; `== 0` → `0.00 °F  exact`. The word is `--font-ui` 12.5 px `--text-muted`; the
tone stays neutral `--text` in all three — **neither `--danger` nor `--success`**. The minus is a
real U+2212 (`forecast.js:55` already defines `MINUS`).

## Patterns to follow

- **`forecast/build.py` is the template for `forecast/history.py`**: pure function, injected
  `generated_at`, an explicit **total** lowercase→UPPERCASE model map (`model_case_map:82`) that
  *raises* rather than `.get()`-ing a default, and `validate_*` run on the way out so a malformed
  document never reaches a caller.
- **`forecast/weights.py:231`** for weight loading. Never re-derive; never `blends[0]`.
- **`forecast/refresh.py:87-93, 107-137, 200-244`** for the CLI: `now_utc()` isolated in one named
  function, argparse, `main(argv) -> int`, `if __name__ == "__main__": sys.exit(main())`.
- **`score/run.py`'s "validate before writing"**: `write_atomic` validates, writes a dotfile beside
  the target, then `os.replace`.
- **Every guard is an explicit `raise` with a message naming the offending path and *why* the rule
  exists** — `score/join.py:174-180` and `forecast/weights.py:178-186` are the house style.
- **Compute from the payload, hardcode nothing.** F5's fixture is deliberately hostile: its
  zero-weight model is NAM (live it is GFS) and its `best_single_model` varies by lead (live it is
  HRRR three times). Any hardcoded `HRRR` renders correctly against live data and **lies** on the
  fixture. `best_single_model_by_lead` must be read from `results.json`, never typed.
- **`repo_relative_source_path`** (`forecast/build.py:279`) for `weights_source.path` — an absolute
  path prints the operator's home directory onto a customer-facing page and makes two correct runs
  differ byte for byte.
- **Prove a grep guard by injecting the banned token into the real file and watching the suite go
  red, then restoring byte-identical.** Three prior guards in this project looked real and were not
  (F1's gate, F4's phantom AST check, the demo team's `prefers-color-scheme` split) — see the
  `forecast-page-ui` retrospective.

## Patterns to avoid

- **`blends[0]`** — the OOS leaderboard leader, differing from the fitted winner at all three leads.
- **A per-model sort before `merge_asof`** — `sort_values(["model","valid_time"])` passes a casual
  glance and is wrong (`score/join.py:111`). Another reason to import rather than mirror.
- **Rescaling a weight vector over a subset of models** — a different blend, whose skill numbers do
  not apply. Also: the verb itself is a T29-banned token; reuse `UNCHANGED_VECTOR_RULE`.
- **`Math.abs` on `error_f`** — a cold blend must read as cold (design-target §6; F5's guard at
  `test_forecast_ui_guards.py:1064` already bans it for `improvement_pct`).
- **ASCII hyphen for a negative value** — real U+2212 only; `forecast.js:55` has `MINUS`.
- **Colouring the error** — `warm` and `cold` are findings, not error states. Neither `--danger`
  nor `--success` (design-target §1.6).
- **`innerHTML`** — `forecast.js` uses `createElement`/`textContent` throughout; keep it.
- **Asserting `len(days) == 30`** — it is **32**. See R2.
- **A bare `assert` in `forecast/`**, or the literal substrings `renorm` / `utcnow` / `kelvin` /
  `273.15` / `459.67` anywhere in `forecast/history.py`'s *code* (docstrings and comments are
  stripped by `normalized_code()`, but every other string literal is scanned).
- **A `?fixture=` style query param.** F5 rejected one: a code path whose only purpose is loading
  fabricated data into a page whose entire value is that its numbers are trustworthy.

## Recommended approach

Contract-first, exactly as F3 did it: lock the §10 key set in `forecast/contract.py` (including the
six `meta` additions and the `load_and_validate_history` seam) **before** writing `history.py`, so
the builder and the validator cannot agree on a shared mistake. Then `forecast/history.py` reads
both parquets read-only, **imports** `score.join.join_forecasts_to_obs` rather than mirroring it
(the ±30-minute rule, the offset column, the never-interpolate rule and the 80 % floor all arrive
proven), pivots to one entry per `(valid_time, lead_h, init_time)`, applies
`forecast.weights.load_fitted_weights`'s label-matched vectors, adds the **per-date** zero-match
assertion that `score.join` does not cover, and writes through a validate-then-`os.replace` path.
The UI extends F5's three existing files per design-target §1.6 — no fourth file, because F5's
protected arity gate forbids one and every CSS hook the stepper and table need is already there.

## Scope: M

New Python is ~2 modules' worth (one new file plus a validator block roughly the size of §9's), but
almost every hard part is already solved and importable: the join, the weight selection, the
validator primitives, the atomic write, and the API seam that needs zero edits. The genuinely new
work is the §10 key set, the per-date omission branch (which needs synthetic fixtures because real
data never triggers it), and ~250 lines of stepper/table UI against CSS hooks that already exist.
The two things that could turn this into an L are the frontend-file arity trap (R1 — avoidable) and
the omission branch shipping untested (R3 — the one that has already bitten this project).
