### Router structure (mirrors `/api/results` at `backend/main.py:56-79`)

```python
REPO_ROOT = Path(__file__).resolve().parent.parent
FORECAST_PATH = REPO_ROOT / "data" / "forecast.json"
HISTORY_PATH = REPO_ROOT / "data" / "forecast_history.json"

router = APIRouter()

@router.get("/api/forecast", summary="...", description="...")
def get_forecast():
    return _load_forecast()          # 503 on every failure
```

`_load_forecast()` is one helper shared by FR1 and FR2 so the two endpoints can never disagree about
whether the file is servable:

```python
def _load_forecast() -> dict:
    if not FORECAST_PATH.exists():
        raise HTTPException(status_code=503, detail=MISSING_FORECAST_DETAIL)
    try:
        return load_and_validate_forecast(FORECAST_PATH)
    except ContractError as exc:
        raise HTTPException(
            status_code=503,
            detail=f"data/forecast.json failed the FORECAST-SPEC §9 contract: {exc}",
        ) from exc
```

Note `load_and_validate_forecast` (`forecast/contract.py:837`) already wraps `OSError` **and**
`json.JSONDecodeError` into `ContractError`, so a single `except ContractError` covers missing-file,
unreadable, malformed-JSON and contract-violation. `ContractError` subclasses `ValueError`
(`backend/contract.py:80`). The `.exists()` pre-check earns its place only because it produces a
better `detail` (naming the refresh command) than the raw `OSError` text.

### 503 error-body shape — keep FastAPI's default, do not invent an envelope

```json
{"detail": "No forecast cache at data/forecast.json. Run: uv run python -m forecast.refresh"}
```

`/api/results` already returns exactly this shape (`HTTPException(status_code=503, detail=...)`).
F5's fetch handler and F8's curl examples both read `detail`. A custom envelope would make the two
API families inconsistent for zero gain.

Suggested `detail` strings (each names the reason, per §11):

| Case | `detail` |
|---|---|
| forecast missing | `No forecast cache at data/forecast.json. Run: uv run --no-sync python -m forecast.refresh` |
| forecast malformed / contract violation | `data/forecast.json failed the FORECAST-SPEC §9 contract: {exc}` |
| history missing | `No history payload at data/forecast_history.json. It is built offline (FORECAST-SPEC §10) and is not present in this checkout.` |
| history unvalidatable | `data/forecast_history.json cannot be served: no FORECAST-SPEC §10 validator is available, and an unvalidated history payload is never served.` |
| history contract violation | `data/forecast_history.json failed the FORECAST-SPEC §10 contract: {exc}` |

## Patterns to Follow

- **`/api/results` is the template** (`backend/main.py:56-79`): `.exists()` pre-check → `except ContractError` → `HTTPException(503, detail=...)`, with a docstring stating *why* there is no fallback. Copy the shape, including the reasoning comment.
- **Module-level path constants resolved from `__file__`** (`backend/main.py:27-29`), and a module-level `MISSING_*_DETAIL` string constant for the missing-file message.
- **Named-reason error messages** — `forecast/contract.py` messages already carry the JSON path (`forecast[7].members`). Interpolate `{exc}` and do not truncate it.
- **`forecast/contract.py`'s module docstring style** — state what is deliberately *not* checked and why. `backend/forecast_api.py` should say in its docstring that there is no refetch route and no fixture fallback, so a future reader does not "helpfully" add one.
- **Test convention** (`tests/test_results_contract.py:1-8`): negative tests assert on **message text**, not merely that something raised. Apply this to every 503 — assert the `detail` names the file and the reason.
- **Pure, injected-instant fixture builders** — use `build_fixture_document(generated_at=..., init_time=...)` with pinned datetimes, as `tests/test_results_contract.py` pins `PINNED_STAMP`.

## Patterns to Avoid

- **A `refetch`/POST route, or a 501 stub.** `backend/main.py`'s docstring calls this out by name: "an unpressed route is dead code".
- **Falling back to a fixture or `results.synthetic.json`** on 503. §15's whole point.
- **Verifying the service via `/health`.** A VS Code helper squats :8000, answers `/health` with a byte-identical `{"status":"ok"}` and now serves a "Boreas API" OpenAPI doc. **Identity is `/openapi.json` → `info.title`.**
- **Widening `tests/test_live_guards.py`'s T29 glob** to `backend/`. F3 established that this file is not opened; carry its own scan instead.
- **`.get()`-ing around the casing bridge** (F3 SUMMARY §5). F4 does not index models at all — but if a handler ever reaches into `members`, index explicitly.
- **Reproducing §9's worked example.** Its `blend_f: 78.41` contradicts its own rule 6 (F3 SUMMARY §1). F4 never recomputes a blend, but do not let the example leak into a test's expected value.
- **Adding `httpx2`** to silence `StarletteDeprecationWarning` from `fastapi.testclient`. It is a warning, not an error; pytest is not configured with `-W error` (`addopts = "--strict-markers"` only). Changing `pyproject.toml`/`uv.lock` is out of F4's scope.

## The history endpoint — recommended design

`data/forecast_history.json` is absent **and** no §10 validator exists. §11 requires the endpoint to
be contract-validated; §15 forbids serving an unvalidated payload. Recommended: write the endpoint's
real logic now and resolve the validator **lazily, by name, at request time**:

```python
def _history_validator():
    """F6 adds `load_and_validate_history` to forecast.contract; until then this is None."""
    return getattr(forecast_contract, "load_and_validate_history", None)
```

- Missing file → 503 (checked first, so the message names the real problem).
- File present but validator absent → 503 "an unvalidated history payload is never served."
- Validator present → validate; `ContractError` → 503 naming the path.

**Why this over the alternatives.** It keeps the endpoint's shape, its 503 vocabulary and its tests
in F4 where §11 puts them; it is **impossible** for it to serve unvalidated history; and F6 lights it
up by adding one function to `forecast/contract.py` — **exactly** F6's stated scope, with zero edits
to `backend/forecast_api.py` (which F6's scope line does not include). All three branches are
testable today by monkeypatching a validator in. The alternative — F4 hard-codes an unconditional
503 and F6 rewrites the handler — leaves the endpoint untested and pushes an edit into a file F6 is
not scoped to touch.

## Recommended Approach

One new module, `backend/forecast_api.py`, holding two path constants, four detail-string constants,
one shared `_load_forecast()` helper and three GET handlers, mirroring `/api/results` line for line —
`.exists()` pre-check, single `except ContractError`, `HTTPException(503, detail=...)`. `/api/forecast`
and `/api/forecast/skill` share the loader so they can never disagree; `/api/forecast/skill` returns
`doc["skill"]` verbatim. `/api/forecast/history` carries its real logic now but resolves the §10
validator lazily from `forecast.contract`, so it 503s honestly until F6 adds one function and never
serves an unvalidated payload. Tests point at `tmp_path` by monkeypatching the module-level constants —
the same indirection `/api/results` already exposes via `backend.main.RESULTS_PATH`, adding **zero**
configuration surface for F8 to document (rejected: env vars and `Depends` overrides, both of which
add surface for no gain).

## Scope: S

~120 lines of new module (mostly docstrings, which are a deliverable here per FR6), 2 lines in
`main.py`, ~14 test cases. No new dependencies, no data-shape work, no numeric logic, no UI. Every
risky mechanism — `TestClient` under the pinned stack, CORS on router routes, monkeypatching the path
constant, 405-on-POST, the `2	0` numstat — was verified empirically during this research. The only
judgement call is the history seam, and it is small and reversible.
