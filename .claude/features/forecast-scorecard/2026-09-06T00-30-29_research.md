## Goal

From the day it lands, every recorded cycle writes down what was predicted **before the outcome
exists**, in a committed append-only JSONL ledger, and grades itself against IEM ASOS observations
as they arrive. The scorecard is a pure function of that ledger: what we said, what happened, and
the running score — including the losses, at the same visual weight as the wins.

### The JSONL precedent — `fetch/backfill.py`

## Proposed ledger row schema (concrete)

One file, two `kind`s, every key present on every line, keys in a fixed declared order.

**Prediction row** — written by the record pass, from `data/forecast.json`:

```json
{"kind":"prediction","init_time":"2026-09-04T12:00:00Z","run_label":"12z",
 "valid_time":"2026-09-04T15:00:00Z","lead_h":3,"series":"HRRR","series_kind":"model",
 "forecast_f":86.3708,"weights_fitted_at_lead_h":6,"is_extrapolated_lead":false,
 "source_generated_at":"2026-09-04T20:52:09Z","recorded_at":"2026-09-06T00:30:29Z"}
```

The blend row is identical with `"series":"BLEND"`, `"series_kind":"blend"`,
`"forecast_f": <row.blend_f>`. Row identity is
**`(kind, init_time, valid_time, lead_h, series)`**.

**Grade row** — written by the grade pass, never more than once per key:

```json
{"kind":"grade","init_time":"2026-09-04T12:00:00Z","valid_time":"2026-09-04T15:00:00Z",
 "lead_h":3,"series":"HRRR","status":"graded","observed_f":84.0,"obs_offset_min":-8,
 "error_f":2.3708,"abs_error_f":2.3708,"reason":null,
 "obs_source":"iem_asos_OMA","tolerance_min":30,"graded_at":"2026-09-06T00:30:29Z"}
```

A **gap** is the same row with `"status":"gap"`, `observed_f`/`obs_offset_min`/`error_f`/
`abs_error_f` all `null`, and `reason` a non-null sentence
(`"no observation within ±30 min of 2026-09-04T15:00:00Z"`). A gap is only written once the row can
never become gradeable — recommend `now - valid_time > GAP_GRACE` (3 h, comfortably past ±30 min
plus IEM publication lag). Until then the row is simply **`pending`** — the absence of a grade line,
not a line of its own.

`error_f` is **signed** (`forecast_f − observed_f`) so bias is visible, matching
`forecast/history.py`'s §10 convention; `abs_error_f` is carried so no consumer re-derives it.

Read rule: build a map keyed by row identity. **Latest-wins for `prediction`** (backfill's
convention). **First-wins for `grade`** — a grade is never superseded. Since the *writer* refuses to
append a second line for any existing key, the two rules are observationally identical on any ledger
this code produces, and a test pins exactly that.

## The endpoint

```python
# backend/forecast_api.py -- appended below get_forecast_history, on the EXISTING router
@router.get("/api/forecast/scorecard", summary=..., description=...)
def get_forecast_scorecard():          # NO return annotation -- guarded
    return scorecard_module.serve_scorecard(now=..., deadline_s=...)
```

`serve_scorecard` lives in `forecast/scorecard.py` and does, in order:
1. **record** from `data/forecast.json` if that `init_time` is not already in the ledger (pure disk,
   zero network, no deadline concern);
2. **grade** everything newly gradeable, under the wall-clock deadline, swallowing **any** fetch or
   join failure into a per-row skip reason;
3. return **`scorecard(load_ledger(...), now)`** — the pure function.

**Never 503 on a network failure.** A missing ledger is an empty ledger → 200 with
`"enough": false, "not_enough_reason": "not enough days yet, 0 recorded"`. Reserve 503 for the
scorecard failing its own validator — a real bug, mirroring `/api/forecast`'s contract branch.

### The wall-clock deadline — where it lives and a sane value

**Measured, not guessed** (3 live calls, this machine, just now): the IEM 2-day slice returns in
**0.95 / 1.03 / 0.95 s**, 12,949 bytes.

Recommendation:
```python
HTTP_TIMEOUT   = (3.05, 5.0)   # (connect, read) -- requests' per-socket-operation bound
GRADE_DEADLINE_S = 6.0         # total wall clock for one lazy pass
```
`GRADE_DEADLINE_S` is checked **before** the fetch is issued and again before any subsequent work.
**There is exactly one HTTP request per pass** (one IEM slice covers the whole ungraded window), so
total wall clock is genuinely bounded by `connect + read` — no thread, no future, no timer.
That matters: the ticket forbids a background thread, and `future.result(timeout=…)` would leave a
hung worker behind. `requests`' `timeout` is per-socket-operation, not total; the single-request
design is what makes that distinction safe to rely on.

**FastAPI is sync here**, so a `def` handler runs in Starlette's anyio worker threadpool. A bounded
6 s block occupies one worker and does not stall the event loop, so `/api/forecast` keeps serving.

## Patterns to Follow

1. **`fetch/backfill.py:154-193`** — `append_ledger` / `load_ledger` verbatim in shape: `mode="a"`,
   flushed, module-level lock; missing file → `{}`; truncated final line → `continue`, never raise.
2. **`forecast/history.py:298-320`** — the per-step observation dict. The join has no `by=`, so all
   four members at one step share one observation; history.py **asserts** they do. **This is how the
   blend gets graded**: join the four members, then attach the blend to that step's `observed_f` and
   `obs_offset_min`. (`canonical_model_name("BLEND")` **raises** — see R2.)
3. **`forecast/history.py:21-26`** — "the join is imported, never mirrored." A local
   `sort_values(["model","valid_time"])` before `merge_asof` looks right and is wrong

4. **`forecast/history.py:466-497`** (`_join_block`) — publish the match counts *in the payload*
   rather than leaving them to be trusted, and cross-check them against the join's own diagnostics.
5. **`backend/forecast_api.py:89-109`** — read + validate on **every** request from a module-global
   path constant, so a test can repoint it and an offline pass is picked up without a restart.
6. **`tests/test_forecast_skill_panel_copy.py`** — the four-layer copy guard: **containment first**
   (all prose in one delimited block, no long string literal outside it), then byte-pinned copy,
   then a claims blacklist **with a sanctioned-phrase allowlist**, then per-sentence markers. Its
   docstring also models stating what a guard *cannot* see.
7. **`backend/forecast_api.py:112-121`** — F4's lazy `getattr` seam. F6 lit up
   `/api/forecast/history` with **zero** edits to `forecast_api.py`. F9 cannot use it (a new route

   put the scorecard validator in `scorecard.py` and import `BANNED_FIELD_NAMES`.
8. **`forecast/refresh.py:107-138, 200`** — the CLI shape: `main(argv=None) -> int`, named exit

9. **Every guard is an explicit `raise`** (`score/join.py:33`) — `python -O` strips `assert`.
10. **`tests/test_forecast_ui_guards.py:1197`** — `baked_payload_literals`. Model names, the site

## Patterns to Avoid

- **Appending F9's JS/CSS at the tail of the file.** `forecast.js:862-865` says it outright: F6's
  extractor slices from its banner to **end of file**. F7 placed itself above that banner; F9 must
  too.
- **Typing a model name in `forecast.js`.** `test_whole_forecast_js_still_bakes_in_no_payload_literal`
  greps `\bHRRR\b` etc. over the **whole** stripped file. Per-model rows iterate
  `meta.models_included`. Likewise no literal `16`, no site name.
- **Re-implementing the ±30-minute join**, or calling `pd.merge_asof` directly.
- **Calling `fetch.obs.write_obs`** — its 700-distinct-hour floor is for the 30-day backfill and
  will raise on a live 2-day slice.
- **A rolling average, an EMA, or any smoothing** over the record (§15, floor #8).
- **Rewriting or compacting the ledger.** No `open(…, "w")`, no `write_text`, no `truncate`, no
  `os.replace` on the ledger path. (`write_atomic` is right for `data/forecast.json`; it is
  **wrong** here — atomic replace *is* truncation.)
- **A background thread / `ThreadPoolExecutor` future** to enforce the deadline. Explicitly banned,
  and it leaves a hung worker behind.
- **Naming a refit cadence.** §22.1 is deliberately open. No "weekly", "monthly", "every N days".
- **Padding the record from the backtest.** F6's history is a *backtest replay*; F9's ledger is
  forward-validated. Seeding one from the other destroys the entire claim.

## Recommended Approach

Build `forecast/scorecard.py` as three strictly separated layers, because the acceptance floor is
really a purity argument: **(a)** an append-only ledger writer that mirrors `fetch/backfill.py`
line for line and never opens the file in anything but `mode="a"`; **(b)** an impure `record` /
`grade` pass — record reads `data/forecast.json` and writes 80 prediction rows per cycle; grade
reads the ledger, offers only in-coverage member rows to the **imported**
`score.join.join_forecasts_to_obs`, attaches the blend to its step's observation the way
`forecast/history.py:298-320` does, and appends grade rows under a 6 s wall-clock deadline with one
bounded `session_get`; **(c)** `scorecard(rows, now)`, pure, reading nothing but its arguments, which
both the CLI and the endpoint call. `serve_scorecard` composes (b) then (c) and swallows every
network failure into `pending`. The UI is a new `<section>` after the history section, with JS and
CSS inserted **above** the F6 banners, rendering per-cycle results, per-model realized MAE beside the
blend's, and the beaten-streak counters at identical type scale and colour role for wins and losses.

This over the alternatives because: a separate grading daemon is banned and dies silently; a
merge-off-`merge_asof` reimplementation contradicts §3's "reuse, do not rewrite" and re-opens the
exact bug `score/join.py:111` documents; and putting the fetch wrapper in `backend/forecast_api.py`
trips a protected guard. Committing the ledger is not a preference — a gitignored track record is
one `git clean` from erasure, which is the single way this ticket could be made to look better
than it was.

## Scope: L

Roughly 700-900 lines of new Python across one module, one endpoint handler, ~250 lines across the
three frontend files, two committed fixture ledgers plus a canned IEM CSV, and **~44 tests across
3-4 new modules plus one widened existing guard**. The module itself is moderate; the acceptance
