## Architecture

### Summary

Add `frontend/overview.html` as a **sibling** of the untouched product page, plus `overview.css`,
`overview.js` and a shared `theme.js`. Both pages read one appended `[data-theme=dark]` block in
`frontend/tokens.css` and one shared theme toggle. Every result number on the overview is bound
declaratively from a single live `GET /api/results` read; the HTML ships `—` as its only literal, so a
dead backend degrades to prose automatically rather than to a blank page. The one piece of real
engineering is that the **product page** memoizes its model→colour map (`models.js:14-24`) and bakes
resolved hexes inline, so a working dark mode needs `resetColors()` + a full re-render on toggle — the
overview sidesteps this entirely by using `style="fill: var(--model-hrrr)"` in its SVG instead of
resolved hexes.

### Data Flow


### The declarative binding contract (locks Stream 2 ↔ Stream 3 ↔ prose)

`overview.html` contains **no result numbers**. Every live value is a placeholder:

```html
<span class="num" data-live="per.24.winner.mae_oos" data-fmt="degF">—</span>
<span data-live="meta.window.days">—</span>
```

`overview.js` builds one view-model, then walks `document.querySelectorAll('[data-live]')`, resolves the
dot path, formats via `data-fmt` (`degF` | `pct` | `int` | `date` | `raw`), and writes `textContent`.
**If the fetch fails, the walk never runs and every placeholder stays `—` (FR8, free).**

**View-model shape — locked before either side is written:**

```js
vm = {
  meta:  payload.meta,                       // site, window, split, source, generated_at, is_synthetic
  leads: payload.lead_times,                 // [6, 12, 24]  — ints
  per: {                                     // keyed by String(lead). NAMED TRAP: app.js:22-24
    "6": {
      nBlends,                               // L.blends.length            (286, never hardcoded)
      nSamples: {train, test},               // L.n_samples
      join: {matched_pct, mean_abs_offset_min},
      models: [...],                         // L.models, sorted asc by mae for "two best singles"
      bestSingle: {model, mae_oos},          // L.best_single_model
      winner: {label, mae_oos, improvement_pct},
      winnerRank,                            // blends.find(b => b.label === winner.label).rank
                                             // NEVER blends[0] — was 5/23/5 of 286 on this run
      dropGfs,                               // findBlend(blends, {HRRR:.4, GFS:0, NAM:.3, NBM:.3})
      dropGfsImprovementPct                  // see integrity guard below
    }, "12": {...}, "24": {...}
  }
}
```

**Integrity guard on the one derived number.** `dropGfsImprovementPct = (bestSingle.mae_oos −
dropGfs.mae_out_of_sample) / bestSingle.mae_oos × 100`. Before using it, apply the same formula to the
winner and assert it reproduces `winner.improvement_pct_vs_best_single` to 2 dp. If it does not, render
raw MAEs only and suppress every drop-GFS percentage. (Verified against this run: winner 6 h →
9.0249 ✓; drop-GFS 6 h → 5.742%, matches README §5.1.)

**Null-safety.** `winnerRank` and `dropGfs` are lookups that can miss. On a miss the bound element
stays `—` and the surrounding sentence is written so it still reads correctly without the number.
Never `blends[0]`, never an interpolated value.

## Key Decisions

1. **Sibling page, not a new index.** `overview.html` is one more static file; `smoke_ui.sh:20` opens `/` and asserts the product DOM. Repointing `/` turns a green smoke check red for a cosmetic reason, hours before a demo. (D1, R2)
2. **Seven sections, not twelve.** Condensed from research D7, each one idea, built around the two takeaways — *which models to use for a specific forecast* (§2-§6) and *this could be sold as an API* (§7). §7 is a takeaway, not an epilogue.
3. **Declarative `[data-live]` binding, with `—` as the only literal in the HTML.** Makes FR7 (no hardcoded numbers) structurally enforced rather than review-enforced, and makes FR8 (degrade to prose) free.
4. **Overview diagrams use CSS custom properties, never resolved hexes.** This sidesteps the `models.js` memoization trap entirely on the new page; only the existing product page needs `resetColors()` + re-render. Large risk reduction for one design choice.
5. **`resetColors()` + full re-render is an acceptance criterion, not polish.** A token block alone gives a dark background with a light-palette page. This is the single most likely way dark mode ships broken. (D5, R1)
6. **No `prefers-color-scheme`.** Clarity §4 forbids it, and a theme that flips under a presenter mid-demo is worse than one that doesn't. Explicit toggle, `localStorage['internal-portal:theme']`, inline pre-hydration script. (This resolves the task brief's Q8 in favour of the governing design system; the toggle and the persistence key are exactly as the user specified.)
7. **The GFS caveat renders live via `findBlend`.** Research verified `HRRR 0.4 / GFS 0.0 / NAM 0.3 / NBM 0.3` is a real lattice point at ranks 17 / 4 / 1 of 286. The most credible section on the page therefore needs zero hardcoded numbers and cannot drift after a re-run.
8. **The verdict sentence in §6 is assembled from a runtime comparison.** A re-run that reverses the finding must be able to say so without an HTML edit.
9. **Solid light backplate for the S2 mark in both themes.** §6b permits a backplate and forbids recolouring; `filter: invert()` is rejected. One asset, theme-invariant, no image editing.
10. **One revertible commit, path-scoped.** `git revert <sha>` restores the current green tree whole. (D8)
